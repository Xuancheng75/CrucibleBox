## 架构决策

- 保留现有仓库布局。宿主应用层装配桌面和安装生命周期，协议 crate 拥有纯路由与契约，runtime crate 拥有 transport 和进程监督，SDK 只依赖公开契约与传输。平台内建能力始终经过宿主权限裁决，插件导出能力只可经声明的服务目标寻址。
- 第一轮扩展 `exports/dependencies`，继续使用现有包布局、Manifest/API 6 和 wire 4，独立验证选择规则。版本号到正式冻结时按实际破坏面统一调整。`providerId` 指定固定提供者；省略时只匹配声明可互换的能力，按接口 SemVer 降序及插件 ID 升序确定选项。涉及私有输入或持久状态的消费者应固定可信提供者。能力发现与调用共享解析，结果只描述当前绑定，不承诺进程健康或随后调用成功。
- 能力候选来自启用记录和经过许可验证的清单。发现、安装变更和启动不依赖同一个 Worker 锁。启用前验证拟变更节点及受影响依赖链；运行时按请求验证消费者、候选和实际执行边界。Provider 故障报告给相关调用方，任务持有提交时的目标。暂不引入自动重试或热迁移 Provider 状态。
- 保留原生可信本地代码和 QuickJS 受约束脚本的区别。Worker Job Object 管理进程树；身份、会话、目标和文件授权来自宿主。能力提供者不获得替换宿主安全 API 的权力。公开服务调用与任务不采用输入指定调用者身份。
- 延续有界 JSON 帧和受管文件引用，事件与取消通过同一会话/所有权模型扩展。大文件优先使用受管引用和已有限流，避免扩大 JSON 帧预算。后台服务采用显式启动策略和进程监督，启动顺序按已解析依赖。
- VS Code 的声明式激活区分按需与启动完成事件，适合借鉴触发时机；保持本地启动策略的触发集合小而清楚。[VS Code 激活事件](https://raw.githubusercontent.com/microsoft/vscode-docs/main/api/references/activation-events.md)
- Theia 以标识收集贡献并限定容器作用域。CrucibleBox 的跨进程供应者需要按已授权清单和版本索引，当前 Rust registry 足以承载，避免复制依赖注入容器。[Theia ContributionProvider](https://raw.githubusercontent.com/eclipse-theia/theia/master/packages/core/src/common/contribution-provider.ts)

## 实施和数据保护

1. Phase 1 先验证真实服务提供者、消费者、查询、任务调用和坏包隔离，随后分离内建分发；把 SDK 与共享 Schema 一同测试。
2. Phase 2 完成后台恢复、按需启停和实际 native/JS 进程验证。Phase 3 加入会话事件、取消和大数据端到端测试。Phase 4 逐项扩展文件、网络、进程、日志、存储、资源与真实运行环境。
3. Phase 5 补 UI 扩展点和 SDK/模板交付，Phase 6 在独立插件仓库适配并运行真实业务。Phase 7 完成压力、权限、迁移和故障隔离验证。Phase 8 汇合文档、版本和发布门禁。
4. 开发使用 `.workbench` 下的夹具和临时数据。生产迁移前使用项目的 SQLite 在线备份与成对恢复工具，检查 `integrity_check`、任务结果、插件身份、配置、KV、用户文件及升级/回退。出现两个有数据的目录时保留两者，恢复到独立路径进行核对，后续处置由用户决定。见 [install-recovery.md](install-recovery.md)。

## P0 协议草案与风险

| 边界 | 选型与契约 |
| --- | --- |
| Renderer 到宿主 | opaque iframe 通过 MessagePort 到可信主窗口。主窗口绑定实际挂载会话后调用 Tauri，宿主在当前安装与会话上授权。renderer 的递增 wire ID 用于拒绝重放，SDK 相关 ID 由帧桥映射回客户端。 |
| 宿主到 Worker | 沿用 stdin/stdout 的 uint32 大端长度前缀和有界 UTF-8 JSON。`hello → initialize → ready` 区分 wire/API 协商、初始化和就绪。标准请求包含 `wireVersion`、`requestId`、`session`、`target`、`method`、`params`，响应关联同一请求 ID，返回结果或 `{code,message}`。stdout 保留给协议。 |
| 能力调用 | `target.kind = service` 携带 capability ID，Provider、调用方身份和请求上下文由宿主决定。`capabilities.resolve` 返回当前绑定。P1 在 `exports.methods` 加入输入输出 Schema 与上下文，允许保留已有字符串方法。平台权限仍来自公共契约和安装许可。 |
| 任务、事件与大数据 | 任务沿用稳定 owner、选定 Provider、取消确认与持久任务结果。后续事件协议绑定会话并定义权限、顺序和缓冲上限。大文件以受管引用跨越进程，采用有界帧传输控制信息。详见现有 [公共契约](../contracts/next2/contract.json) 和 [Worker](../src-tauri/crates/next2-runtime/src/worker.rs)。 |

| 风险触发 | 处理与验证 |
| --- | --- |
| 老版本安装包或 SDK 与新行为混用 | P1 保留既有 Manifest/API 6、wire 4 和数据 schema 1。仅 2.2.0 支持的新字段通过 `minHostVersion` 声明。接口冻结时再完成宿主与公开 SDK 的版本对齐。 |
| 同名 Provider 或兼容范围包含多个版本 | 按接口 SemVer 和插件 ID 确定选择。需要固定身份或持久状态时声明 `providerId`。已排队任务保留所选 Provider 包版本，安装替换导致过期路由时明确失败。 |
| 安装包损坏、Schema 非法或 Provider 输出不合约 | 仅纳入通过审批的清单。执行时保留文件摘要、信任和 owner 检查。Manifest 限制 Schema 语法、大小和深度，执行入口检查参数和结果，测试恶意 `$ref`、错误上下文、无关损坏包和替换保护。 |
| Worker 崩溃、后台启动失败或运行时隔离被误解 | 复用 Windows Job Object 和握手。启动失败隔离并记录日志，原生插件仍按当前用户的可信代码处理。空闲崩溃检测和后台主动工作归 P2。 |
| 旧源、目标与数据库 WAL 同时存在 | 用现有在线备份和成对恢复工具准备迁移前副本，隔离核验 SQLite、稳定身份、配置、KV、任务与用户文件。迁移目标已有数据时保留源与目标，先完成核对，再决定切换。 |

阶段实施证据见 [P0/P1 验收](2.2.0-p0-p1.md) 和 [开发记录](2.2.0-platform-progress.md)。
